Splash Host API Evolution

The current aichat generated runsplash uses agent.notify(event_id, payload) as the local reverse channel:

Button {
    text: "+1"
    on_click: || agent.notify("inc", {})
}

TextInput {
    text: "{{state.input.new_item.value}}"
    on_change: |text| agent.notify("app.input.set", {key: "new_item", text: text})
}

This mechanism solves the controlled action boundary from Template to Host. It is not tied to the specific function name. Therefore, if Splash provides a higher-level Host API, the implementation can gradually reduce direct exposure of agent.notify and treat it as a legacy primitive.

Recommended generated code should use semantic APIs:

Button {
    text: "+1"
    on_click: || app.action("inc", {})
}

TextInput {
    text: "{{state.input.new_item.value}}"
    on_change: |text| app.input.set("new_item", text)
}

Button {
    text: "Add"
    on_click: || app.collection.add_from_input("items", "new_item")
}

The Host API should aim to:

  • let generated UI express intent without directly mutating Host internals;
  • provide a stable semantic API surface for common capabilities such as action, input, and collection;
  • let the capability manifest declare API families instead of only free-form event strings;
  • validate payload structure earlier at the API boundary;
  • keep the Host as the data/state owner.

One compatible implementation shape is:

app.collection.add_from_input("items", "new_item")
    -> app.action("app.collection.add_from_input", {collection: "items", input: "new_item"})
    -> internal SplashAction::Notify
    -> Host action dispatcher

In other words, agent.notify may remain as an internal transport primitive at first, while generated code should prefer the app.* API. After the Host API becomes stable enough, agent.notify can be reserved for debugging, low-level compatibility, or restoring old messages.

The boundary remains unchanged:

  • Host API calls must pass action whitelist and payload schema validation.
  • Unknown API/action calls must be logged and ignored.
  • Draft state in input fields must not rewrite the runsplash source on every keypress.
  • Local Host API must not be used to submit remote shared fact actions in scenarios such as Robrix2.
  • Remote shared actions should still use their corresponding transport binding, such as org.octos.action_response.

Discussion Synthesis: Makepad/Splash Agent2App Roadmap

The discussions expand Agent2App from an aichat demo into three mutually reinforcing engineering tracks:

Local AppGen:
    aichat generates inline runsplash views

Room AppGen:
    Robrix/Matrix hosts shared, persistent, collaborative app views

Software Factory:
    component skills, Host APIs, test harnesses, and model evaluation loops produce working apps

The shared conclusion is that Makepad should not be framed only as a Skia replacement or a Flutter-like UI toolkit. The stronger story is that Makepad + Robius + Splash can become a cross-platform native app runtime for the AI era. Splash is not meant to replace Rust for every piece of logic; it gives AI a low-token, streamable, recoverable, Host-embeddable executable template language.

flowchart TB
    Core[Agent2App Core Kernel]
    Core --> Local[aichat Local AppGen]
    Core --> Room[Robrix Matrix Room App]
    Core --> Factory[AI App Software Factory]

    Local --> RS[runsplash inline view]
    Local --> HS[Host-owned data/state]
    Local --> API[Splash Host API]

    Room --> MX[Matrix event/state binding]
    Room --> Shared[shared room data]
    Room --> Personal[personalized view per user]

    Factory --> Skills[component skills]
    Factory --> Harness[model-specific harness]
    Factory --> Tests[headless/remote UI tests]

AI-native Runtime, Not a Traditional Framework

Traditional frameworks assume that the primary author is a human. Agent2App assumes that the primary generator is a model, which changes the constraints:

  • model context windows are limited;
  • model capability varies widely;
  • models have little Splash training data;
  • generating UI and generating reliable app logic have different difficulty profiles;
  • generating a full Rust/HTML/JS app in one shot can work, but it is slow, expensive in tokens, and exposes a larger error surface.

The goal for Splash should therefore be:

the lowest-token executable app representation

The model generates a shorter Splash template, the Host provides data/state/action/API boundaries, and the runtime plus test harness handle reliability.

Harness Strength Should Vary by Model and Target

The recurring term in the discussions is harness. Here, harness means more than a prompt. It is a dynamically selected constraint package based on model, target device, AppType, available components, and error feedback:

model capability
target device
AppType
component skills
Host API manifest
runtime error feedback
test result
    -> selected harness/context

Strong frontier models can be allowed to generate more original structure. Smaller or local models should be constrained by stronger templates, fixed components, and less freedom. For weak models, the recommended path is not to create a complete app from scratch, but to:

select components
fill configuration
generate a small delta
call Host APIs

This reduces creativity but improves usability. The baseline should be reliability and usefulness; advanced visual effects can be enabled according to model ability, time budget, and device capability.

Component Skills Are Reusable Assets

If the model regenerates calendar, todo, weather, poll, trip planner, or mission room widgets from scratch every time, context grows and quality becomes unstable. A better shape is:

App request
    -> semantic routing
    -> load relevant component skills
    -> model emits config/delta
    -> Host/Splash runtime composes final view

Candidate component skills include:

  • Todo / collection
  • Calculator
  • Timer
  • Calendar / agenda
  • Poll
  • Trip planner
  • Barcamp scheduler
  • Mission room
  • Dashboard / -1 screen card

A component skill can include Splash snippets, Host API wrappers, schema, examples, and test fixtures. Longer term, the project can generate and publish a large Splash example corpus so future models, LoRA adapters, or retrieval contexts can learn Splash more reliably.

State Owner Must Be Host or Room, Not Generated Widget

Generated apps are transient. If business state lives inside a Splash widget instance, it can be lost when the timeline scrolls, the widget is recycled, or the view is regenerated.

The correct boundary is:

Host / Matrix room owns data and shared truth
HostState owns local draft and view state
Splash owns the current view template
Widget instance owns only transient rendering state

This means PortalList or timeline recycling is not a protocol problem. Visible widgets may be freed; AppInstance, DataSnapshot, and HostState must live at a higher layer.

Robrix/Matrix: From Webview Widgets to Splash Room Apps

Matrix already has a widget concept, but the current shape is closer to iframe/webview apps. It can access room state and support collaborative examples such as schedules, but it is heavy, client support is expensive, and ecosystem usage is low.

Robrix + Splash can provide a lighter native room app binding:

Matrix room event / room state
    -> Robrix validates org.octos.app envelope
    -> Robrix creates AppInstance
    -> injects scoped room data into Splash VM
    -> renders Splash view inline in room
    -> user action goes through Host API
    -> producer writes Matrix event/state update
    -> all clients re-project data into their own view

sequenceDiagram
    participant A as Agent
    participant M as Matrix Room
    participant R as Robrix Host
    participant VM as Splash VM
    participant U as User
    participant P as Producer

    A->>M: org.octos.app + Splash template
    R->>M: read room event/state
    R->>R: validate AppType, scope, capabilities
    R->>VM: inject room data projection + Host API
    VM->>U: render inline room app
    U->>VM: click/type/drag
    VM->>R: app.action(...)
    R->>R: validate action and payload
    R->>P: submit shared action
    P->>M: new DataSnapshot/action event
    R->>VM: refresh projected data

This supports two important capabilities:

  • multiple room members can collaborate on the same shared data;
  • each user can render the same data through their own view/template.

For example, a family trip planner can share itinerary, participants, and tasks while each member uses a different layout: calendar view, map-first view, task list, or compact card.

Matrix is a transport binding, not the protocol kernel. The Agent2App kernel still defines AppInstance, DataSnapshot, Template, Action, Scope, and Permission. Matrix binding decides how to encode those concepts into room events, room state, or widget-like events.

Matrix Splash App as a Room Artifact

One concrete landing point is that Splash script can be part of room content instead of an external app package.

Example shape:

{
  "org.octos.app": {
    "type": "room_poll",
    "version": 1,
    "scope": "room",
    "app_id": "poll.dinner",
    "data": {},
    "template": {
      "format": "splash",
      "code": "RoundedView{ ... }"
    },
    "capabilities": ["app.action", "app.collection"]
  }
}

This lets Robrix treat Agent-generated views as rich interactive chat/room content, not as separately installed applications.

Software Factory: From Demo to Verified Production Line

The later discussion moves toward a software factory. The goal is not to manually fix a calculator demo, but to build a repeatable pipeline:

App spec
component skills
model-specific harness
generated Splash/Rust artifact
headless or remote UI run
virtual click/type/scroll
state/action assertions
runtime errors
    -> feedback into harness

flowchart LR
    Spec[App spec] --> Ctx[model harness/context]
    Ctx --> Gen[generate Splash/app artifact]
    Gen --> Run[run in headless or remote Host]
    Run --> Act[virtual click/type/scroll]
    Act --> Assert[state/action assertions]
    Assert -->|pass| Keep[accept harness/app]
    Assert -->|fail| Err[collect runtime errors]
    Err --> Tune[mutate context or component skill]
    Tune --> Gen

This moves Agent2App from "can the model draw UI" to "can the model produce a working app". The test target must go beyond parse/render:

  • button clicks must emit the correct action;
  • input must preserve focus and draft state;
  • collection add/toggle/delete must change Host data;
  • calculator operator/equal/clear must be correct;
  • timer start/pause/reset must be correct;
  • state template refresh must not rewrite input source on every keypress.

Makepad-native widgets can use a unified automation path. Platform-native widgets need per-platform adapters because iOS, macOS, Android, and WebView differ in lifecycle, query, event injection, and compositing behavior.

Splash Streaming Eval and VM Hardening

The current simple streaming eval strategy keeps trying to evaluate, ignores errors, and retries until the code becomes complete. This works, but it is noisy and can enter unrecoverable states.

Hardening directions:

  • evaluate only on complete scope/block boundaries;
  • incomplete scopes must not create fatal state;
  • infinite loops, timeout, and memory overuse must be interruptible;
  • VM errors must be returned structurally to the harness;
  • the streaming parser should identify complete widgets, complete let bindings, and complete callbacks;
  • repeated eval should reuse stable parts where possible to reduce flicker and focus loss.

These are not kernel requirements, but they are runtime quality gates for the aichat and Robrix profiles.

Native Components and Platform Compositing Boundaries

Makepad can wrap native components and can also provide Makepad-native widgets. These two paths have different boundaries.

On Apple platforms, native component contents often cannot be read by the application and then warped by a custom shader glass effect. The system compositor protects content such as Safari or banking views. Apps can overlay transparent content, but readback-based refraction or blur generally requires the Apple system compositor or screen capture permission.

Profiles should therefore distinguish:

Makepad-native widget:
    cross-platform rendering, unified testing, Makepad shader/glass/vector effects

Platform-native component:
    system capability reuse, but testing, compositing, and permissions are per-platform

Everything React Native can wrap, Makepad/Robius can in principle wrap too; glass, readback, snapshot, and automation need platform-specific handling.

Vector, SVG, and Shader Boundaries

The discussions also compare SVG, Splash vector drawing, and shaders. The conclusion is not that Agent2App must generate SVG:

  • small animated UI elements, icons, arrows, and micro interactions fit shaders;
  • large complex graphics should not abuse shaders;
  • complex shapes such as a tiger or logo are better handled by vector/raster pipelines;
  • Splash can expose a Makepad-native vector/shader DSL that is simpler than SVG for generated UI;
  • standardized SVG is optional if the target runtime has a concise, stable native expression.

This supports a broader principle: Agent2App Template should not be bound to Web/SVG encoding. Makepad-native template encoding is a first-class path.

Distribution and App Store Boundary

The discussions form a cautious reading of Apple policy: the risk is not interpretation itself, but whether the app lets users download, generate, and execute new code that changes app functionality after review.

High-risk framing:

Generate any app
AI app store
Run arbitrary downloaded applications
Replace App Store

Lower-risk framing:

AI chat with rich interactive content
Room-native collaborative widgets
Configurable mini apps inside a declared Host
Predeclared calendar/poll/collection/dashboard capabilities

Product language should emphasize agent2view, not agent2project. The Host's primary purpose should be declared as chat, collaboration, or room interaction. Splash/A2UI views are rich content under that purpose, not a general-purpose app store replacement.

Android and Web/WASM can be more aggressive. iOS App Store builds should prefer predeclared capabilities and configurable widgets. TestFlight, Web demos, Android sideload, and desktop builds can be used as freer experimentation channels.

Recommended Milestones

Phase 0: Local AppGen
    aichat reliably generates runsplash views with Host API, state projection, and basic actions.

Phase 1: Host API
    app.action / app.input / app.collection / ai.talk replace direct public use of agent.notify.

Phase 2: Verification Harness
    calculator, todo, timer, poll, and calendar enter the automated headless/remote test suite.

Phase 3: Component Skills
    common mini apps become component skill + schema + examples + tests.

Phase 4: Robrix Room App
    Matrix events carry app envelopes and Splash templates; Robrix renders them inline.

Phase 5: Shared Collaboration
    actions write back to Matrix events/state; users share data while keeping personalized views.

Phase 6: Distribution Strategy
    Web/WASM and Android show the full dynamic runtime first; iOS uses rich chat content with predeclared capabilities.

Open Decisions

  • Final naming for Splash Host API: app.*, host.*, or profile-specific namespace.
  • Matrix room app event schema: template in event content, room state, or both.
  • AppInstance lifecycle: timeline visibility, room membership, permission changes, history restore.
  • VM resource limits: CPU, memory, timer, network, file, native API.
  • Component skills packaging: plain text, repo artifact, Matrix event, or Host-bundled library.
  • Minimum app suite and scoring rules for per-model harness eval.
  • App Store wording and product capability boundaries.

These issues do not block the current protocol kernel, but they decide the product path for aichat and Robrix profiles.
